# File size: production lines capped, test modules split by theme, one crate `test_support`

Answers issue #82. Amends nothing; ADR-0006 references it for module layout, ADR-0008 is unaffected.

Fourteen files in `src/` exceed 600 total lines (measured `main` `ebbda8b`); the worst, `research/agent_loop/runner.rs`, is 2086. Splitting by line count alone (e.g. a mechanical half-and-half cut) would sever functions from the state they close over. Looking at production code only, just four files exceed 500 lines (`governor.rs`, `runner.rs`, `reply.rs`, and `fanout.rs`'s single 320-line async function); the rest of the bulk is `#[cfg(test)] mod tests` sitting inline at the bottom of its file, duplicating the same `EnvGuard` and raw-TCP canned-HTTP-server helpers in `llm/config.rs`, `llm/client.rs`, `research/run.rs`, `research/agent_loop/runner.rs`, and (a different shape) `web/search/{cache,governor}.rs`.

## Decision

1. **Production code per file: at most ~500 lines, split by responsibility, never by line count alone.** A file over the target gets a `mod.rs`/submodule split along the seams the module doc comment already names (e.g. `governor.rs`'s pacing vs suspension state, `runner.rs`'s turn loop vs tool dispatch), not an arbitrary midpoint cut. A file that is one cohesive responsibility (e.g. `yahoo.rs`'s 408 production lines, one engine's request/parse/paginate) stays whole even past 400; the cap is a signal to look for a seam, not an automatic trigger.
2. **A test module over ~500 lines moves to `<stem>/tests/<theme>.rs`.** The file's own `#[cfg(test)] mod tests { ... }` keeps only shared fixtures and declares its themed children: `mod <theme>;`. Each theme file resolves under `<stem>/tests/` by Rust's normal nested-module path rule (a file `foo.rs` with `mod tests { mod bar; }` resolves `bar` to `foo/tests/bar.rs`), so the tests stay inside the module tree they test, not promoted to a crate-level `tests/` integration-test directory. Fixtures shared only between themed children are `pub(super)` in a `tests::helpers` (or similarly named) child, not re-duplicated per theme.
3. **Shared test helpers live in `#[cfg(test)]` `test_support` modules**, scoped to where they are actually shared:
   - **Crate-level** (`src/test_support.rs`, declared `#[cfg(test)] pub(crate) mod test_support;` in `lib.rs`): helpers used across module boundaries (`llm/` and `research/` both spin up a raw-TCP canned HTTP gateway stub; `llm/config.rs` and `research/run.rs` both guard-and-clear `GATEWAY_*` env vars). One `EnvGuard` (caller-supplied key list, clears on both acquire and drop, and tolerates a poisoned lock by recovering it rather than panicking — both are `governor::test_support::EnvGuard`'s existing, strictly safer behavior, adopted crate-wide; `llm/config.rs`'s and `research/run.rs`'s prior guards panicked on a poisoned lock instead, so this is an intentional hardening of those two call sites, not an assertion-preserving no-op) and one canned HTTP server (`CannedResponse`: status, headers, body, optional delay; `CannedServer::spawn`: always captures each request's raw bytes, so a hit count is `.hits()` and a wire-body assertion is `.requests()[i]`).
   - **Module-level** (e.g. `web::search::cache::test_support`, `web::search::governor::test_support`): helpers meaningful only inside one module's own env-var surface (the governor's 27 `SEARCH_*` pacing/suspension keys, the cache's 3 `SEARCH_CACHE*` keys) keep their own module-local `EnvGuard` type and its existing no-argument `lock()`/`set(pairs)` call sites (used by `cache.rs`, `governor.rs`, `fanout.rs`, `ddg.rs`, `yahoo.rs`), but implement the lock-and-clear mechanics by delegating to the crate `EnvGuard` with their own hardcoded key list, rather than re-implementing the `Mutex`/`clear-every-key` logic a third and fourth time. The two modules keep separate underlying locks (via two separate module-level wrapper types each holding their own crate-`EnvGuard`), preserving today's property that a cache-only test and a governor-only test never block on each other's lock.
4. **The 300-500 target is production lines, not total lines, plus a separate ~500-line cap on each test file (inline module or themed split file).** A file is in bounds when its production code is ≤~500 lines by itself AND every test file touching it (the inline `mod tests` or each `tests/<theme>.rs`) is independently ≤~500. This is why `yahoo.rs` (408 production, 483 inline test lines, 891 total) is in bounds today and not a split target: the production side is one cohesive responsibility under the cap, and its test side is under the cap too. Totaling the two sides and capping the sum would force a split that line 2's "never by line count alone" rule already rejects.

## Considered options

- Cap total lines per file (production + tests), no separate test-module rule: rejected. It is exactly the measurement in the Problem statement above that makes most of `src/`'s "oversized" files look like a crisis when the actual production code is fine; it would force test-only splits on cohesive single-responsibility files like `yahoo.rs`.
- One `tests/` integration-test directory at the crate root, per Rust's conventional layout: rejected. Those tests would lose access to `pub(crate)`/private items (`ThinkingParam`, `ChatRequest`, provider-internal parse functions), forcing a wave of visibility widening with no benefit; `<stem>/tests/<theme>.rs` keeps the existing `#[cfg(test)] mod tests` nesting and its visibility.
- A `trait`-based test double seam instead of a shared canned-server struct: rejected per ADR-0006's "no `trait` until a second real adapter exists" — there is one shape of fake HTTP server needed (configurable status/headers/body/delay, request capture), not two implementations to abstract over.
- Merge the module-level `EnvGuard`s (`cache`, `governor`) directly into the crate one, losing their own lock: rejected. It would serialize unrelated `SEARCH_CACHE*` and `SEARCH_*` governor tests against each other's lock for no correctness benefit; delegating the clear-and-restore mechanics while keeping two locks gets the de-duplication without that regression.

## Consequences

- `src/test_support.rs` is the only place a raw-`TcpListener` canned HTTP server or a caller-keyed `EnvGuard` is implemented; `llm/config.rs`, `llm/client.rs`, and `research/run.rs` import it. `web::search::cache::test_support::EnvGuard` and `web::search::governor::test_support::EnvGuard` keep their existing call-site shapes but delegate to it.
- `research/agent_loop/runner.rs`'s own `spawn_double` canned server was left alone by #82 and migrated to `CannedServer` by #83 (the `runner.rs` split), so #82 did not touch a file #80 was concurrently editing. `registry.rs`'s `spawn_llm_double` went the same way.
- A themed test split (`<stem>/tests/<theme>.rs`) is a tool for when a test module alone crosses ~500 lines, not a default; most current test modules stay inline. `llm/client.rs`'s 631 test lines are the first real candidate and are split under #84 alongside its production split.
- This ADR is a convention, not an enforced lint: no CI check greps for line counts. Revisit if files drift past the cap again without anyone noticing.
